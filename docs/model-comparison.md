# トップのグループ分け: ライブラリとモデルの比べ直し (2026-11-28)

#256 ではモデル 2 つ・動かし方 4 つだけを比べ、GitHub のスター数や保守の様子を見ずに
onnxruntime-node + CLIP ViT-B/32 (Xenova の 8 bit) を選びました。ここでは推論のライブラリを
9 つ、モデルを 18 (それぞれ 32 bit と 8 bit) 比べ直します。

## 結論

**入れ替えません。** 今の CLIP ViT-B/32 より、調整に使っていない 208 枚で有意に当たるモデルは
ありませんでした (同じ画像で対にした検定で、速さと大きさが今と同じくらいのもののうち、いちばん良くて p=0.34)。重複の見分けは、
どのモデルも今より多く間違えます (後で書くとおり、今のモデルに有利な測り方ではあります)。
ライブラリも、onnxruntime-node より速く、ほかが悪くならないものはありませんでした。

ただし 1 つ、前の PR の思い違いが見つかりました。**onnxruntime-node は Bun で、推論のあいだ JS の
スレッドを止めます** (1 枚 75ms のうち 70ms)。#256 には「JS のスレッドの外で動く」と書きましたが、
そうではありませんでした。Bun の Worker に入れると、速さはほぼ同じ (86ms) のまま、止まるのは
1ms になります。#272 で、画像の読み込みからモデルまでを Worker に移しました (下の「次に考えること」の 1)。

## 測り方

- 本番の画像 1,668 枚の手元の写しを、wslc のコンテナの中だけで使いました (外には出していません)
- 前処理はアプリと同じ (`src/lib/server/groups/pixels.ts`: LGTM の印を塗りつぶし、真ん中の正方形を縮める)。
  正規化の平均と分散はモデルごとの値 (SigLIP は 0.5/0.5)
- 精度: 文の調整に使った 209 枚・使っていない 208 枚 (held-out) のグループ、人の場面 90 + 90 枚で、
  文の中心にいちばん近いものが正しい割合。文はモデルごとにその文の側で埋め込み直しました
- 重複: 今のモデルで 0.97 以上だった 18 組 (目で見てどれも同じ写真) と、0.95〜0.97 の 27 組 (目で見て別の写真)。
  モデルごとに一番良いしきい値を選んだときの誤りの組の数
- 速さ: 1 スレッド・1 枚ずつ・31 枚の 2 枚目からの中央値。ほかの測りを止めてから測り直しました
- 8 bit は onnxruntime の動的量子化 (重み uint8)。今のモデルは Xenova が配っている 8 bit のファイル
- 版: Bun 1.4.5 (distroless)・onnxruntime-node/web 1.31.1・@huggingface/transformers 4.3.2・openvino-node 2026.4.1・
  @tensorflow/tfjs-node 4.22.0・candle 0.11.1 (Rust 1.100.0)・Python 側は onnxruntime 1.32.0・open_clip 4.2.2・transformers 5.24.1
- スクリプトは [`docs/model-comparison/` (078a159 の時点)](https://github.com/danything/lgtm/tree/078a1599b0e39a3c786732574ebe8387d0dd2a67/docs/model-comparison)。測り直すときだけ使うので、リポジトリからは外しました (画像・名前・正解の一覧はリポジトリに入れていません)

**今のモデルに有利な点**: グループの文 (`scripts/centroids.ts`) は今のモデルで調整したもので、ほかのモデルに
合わせ直してはいません。重複の 45 組も、今のモデルの値で選んだ組です。そのため「調整 209 枚」と「重複」は
今のモデルが勝ちやすく、比べるときは held-out の 208 枚を主に見ました。

## 入れ替えない理由

決め方は「今より明らかに良く、ほかが悪くならないものがあれば入れ替える」でした。

- 精度: 今と同じくらいの速さと大きさで有意に良いモデルが無い (p がいちばん小さいのは OpenAI B/32 の別の 8 bit で 0.34、TinyCLIP 40M で 0.36)。有意に出た 32 bit の LAION B/16 は 6 倍遅い
- 重複: どれも今より誤りが多い
- 入れ替えの手間: 文の側の埋め込みの作り直し・DB の 1,668 枚の埋め込みの作り直し・重複のしきい値の選び直しと目での確かめ。
  多くは画像の側だけの ONNX が配られておらず、自分で書き出して置く場所も要る

# フリーワード検索: 画像に付ける言葉の作り方 (2026-11-28)

検索の欄に入れた言葉で画像を探します。はじめは「問いを毎回、文字のモデルで画像と同じ空間に埋め込む」形
(sentence-transformers/clip-ViT-B-32-multilingual-v1 など) を考えましたが、持ち主と話して
**画像ごとに言葉を前もって付けておき、検索はその言葉を DB で引くだけ**の形にしました。検索のたびにモデルを
読み込む・外す手間とメモリが要らず、検索は 1 回 3ms ほどです。

## 結論

**今の CLIP の画像の埋め込みと、日本語の言葉 321 個の文の埋め込みの近さで、画像ごとに言葉を付けます** (下の a)。

- 新しいモデルは要りません。言葉の埋め込みは前もって作ってリポジトリに置き (`src/lib/server/groups/tags.json`、
  8 bit で 235KB)、画像の埋め込みはグループ分けで DB に残したものを使います。今ある 1,650 枚にも、起動のたびに
  付け直せます (0.4 秒。100 枚ごとにほかのリクエストに順を譲る)
- 語彙を変えたら `scripts/tags.ts` を流し直すだけです (使い捨てのコンテナで、transformers.js 4.3.2)
- 本番の画像の 22 の問いで、上位の当たりは下の表のとおりです。ものの名前 (ラーメン・ビール・海・ライブ・ピース) は
  よく当たり、細かいもの (雪・コード) や本物が少ないもの (猫・犬) は外れが多いです
- キャプションのモデル (b) は、日本語で出せる大きさのもの (Qwen3-VL-2B) が 1 枚 35〜75 秒・メモリ 4GB を超え、
  出てくる文も LGTM の字に引っぱられて使えませんでした。英語だけのもの (Florence-2) は英文はよく当たるものの 1 枚 25〜90 秒・1.3GB で、日本語にする道 (訳すモデル) が別に要ります
- 画像の中の文字 (c) は、LGTM 以外の文字がある画像が 30 枚中 5 枚と少なく、日本語の読みも崩れるので今は入れません。
  入れるなら PP-OCRv5 (ONNX、検出 + 認識で 20MB ほど) を Worker で動かし、LGTM の印を塗ってから読む形が要ります

## a の付け方

画像ごとに、言葉 321 個それぞれとのコサインを出し、次のどちらかを満たす言葉を付けます (1 枚に 8 個まで)。

- その画像の中で上位 (logit 100 の softmax で 2% 以上) で、かつほかの画像よりその言葉に近い (全画像の平均から標準偏差 1 以上)
- softmax で 0.2% 以上で、ほかの画像よりずっと近い (標準偏差 2.5 以上)

softmax だけ (猫耳の人に猫が付く・言葉の少ない画像が無い) と、平均からの離れだけ (多い言葉ほど付かない:
ラーメンの写真に「ラーメン」が付かない) を比べ、両方を合わせたものにしました。1 枚に平均 4.4 個、
言葉が 1 つも付かない画像は 58 枚です。柴犬・うさぎ・フィギュアなどは人の写真にいくつも付いたので (柴犬は 157 枚、
ほぼ人)、2 つ目の条件だけで付けます (`scripts/tag-vocabulary.ts` の `STRICT`)。

## メモリと速さ

本番と同じ 1,650 枚と埋め込みを入れた DB で、distroless のイメージ (main と、この変更) を並べて測りました (`wslc stats`)。

- 常駐メモリ: 起動して分け終わったあと main 27.5MB → 30.8MB、検索 240 回のあと 28.2MB → 32.9MB。
  検索のときにモデルは読みません (画像のモデルの Worker も、新しい画像が来るまで起きません)
- 検索: API 1〜3ms、ページ 3〜6ms (同じ網の中から)。1,650 枚・タグ 7,300 行ほどなら、表を引くだけで足ります
- 起動のときの付け直し: 1,650 枚で 0.4 秒。100 枚ごとに次のターンに譲るので、そのあいだページは待たされません
  (その前のグループの分け直しの 0.4 秒は前からのもの)
